> ## 3. Dual-WAN failover
>
> ### Tracking and thresholds
>
> Run health checks independently on each WAN interface, forced to that WAN so a probe cannot silently leave through the other uplink. Use three independently operated targets:
>
> 1. `1.1.1.1` (Cloudflare anycast, public reachability).
> 2. `8.8.8.8` (Google anycast, independent public reachability).
> 3. The HQ Renon tunnel endpoint, checked by authenticated tunnel keepalive/BFD on the corresponding overlay.
>
> Send a probe round every **500 ms**, with a **200 ms** response timeout. Each round uses a small probe to each target. Declare WAN1 unhealthy if either both public targets fail in **3 consecutive rounds**, or its HQ overlay misses **3 consecutive** authenticated keepalives/BFD checks. This separates internet path health from tunnel health: on an HQ-only tunnel failure, move the HQ route to the already-up WAN2 tunnel even if WAN1 internet still works. Also fail over the default route if the rolling 2-second window shows packet loss **≥5%**, p95 RTT **>250 ms**, or inter-probe jitter **>80 ms** in **3 consecutive evaluations**. These limits are deliberately well below the incident’s 18% loss and >400 ms jitter.
>
> ### Detection and switchover budget
>
> For a hard path failure just after a successful probe, the first missed round is due within 500 ms. Three misses, each resolved by the 200 ms timeout, establish failure no later than approximately `500 + 500 + 500 + 200 = 1,700 ms` after the cut. The tracked route/policy change is budgeted at **250 ms**. Since the WAN2 tunnel is already established, forwarding resumes after route installation without waiting for IKE negotiation:
>
> ```text
> Worst-case hard-failure detection:       1,700 ms
> Tracked route/policy installation:        250 ms
> Warm-tunnel forwarding convergence:       250 ms
>                                          --------
> Budgeted service-path switchover:        2,200 ms (< 3,000 ms)
> ```
>
> The last 250 ms is a convergence budget for next-hop/neighbor and tunnel forwarding state, not a fresh tunnel handshake. Verify the measured bound during commissioning with link cuts and impaired-path tests. If the backup tunnel is down, the sub-3-second forwarding target cannot be guaranteed; alert on loss of warm-standby state rather than counting that as a successful failover.
>
> ### Failback hysteresis and sessions
>
> Do not fail back on one good probe. Require WAN1 to meet all health thresholds continuously for **300 seconds (5 minutes)**, with no loss/jitter/latency breach and the WAN1 HQ tunnel established, before restoring WAN1 preference. If WAN1 degrades during this hold-down, reset the timer. This prevents the flapping experienced during the storm. Keep WAN2 selected during the hold-down; fail back by changing route preference, then observe for a further 60-second guarded period and revert if health immediately regresses.
>
> Maintain separate overlay tunnels and route tracking on both WANs. A WAN change alters the preferred next hop; established TCP sessions pinned to the old WAN’s public NAT address may reset and must reconnect. Do not promise transport-session continuity across different public addresses. Kiosks use short, bounded HTTPS keep-alive pools (for example, 10-second idle keep-alive), DNS caching for the checkout API, and idempotency keys per payment/checkout attempt. On a connection reset they retry with the same idempotency key and bounded backoff; they never create a new payment intent solely because a response timed out. The API/payment integration must return the prior result for a repeated key. Tunnel-based HQ sessions re-route to the warm tunnel; cloud API sessions reconnect over WAN2.

>   config: Readonly<RetryConfig> = RETRY_CONFIG,
> ): number {
>   if (!Number.isInteger(failedAttempt) || failedAttempt < 1) {

>     config.maxDelayMs,

>   async dispatch(payload: AlertPayload): Promise<DispatchResult> {
>     if (this.delivered.has(payload.alert_id)) {
>       return { final_status: "delivered", attempts: [] };
>     }
>
>     const attempts: DispatchAttempt[] = [];
>     let delayBeforeAttempt = 0;
>
>     for (let attempt = 1; attempt <= this.retryConfig.maxAttempts; attempt += 1) {
>       if (delayBeforeAttempt > 0) {
>         await this.deps.sleeper.sleep(delayBeforeAttempt);
>       }
>       try {
>         await this.deps.sink.deliver(payload);
>         this.delivered.add(payload.alert_id);
>         attempts.push({
>           attempt,
>           delay_ms: delayBeforeAttempt,
>           outcome: "delivered",
>         });
>         return { final_status: "delivered", attempts };
>       } catch (error) {
>         const retryable = isRetryableDispatchError(error);
>         const message = error instanceof Error ? error.message : String(error);
>         attempts.push({
>           attempt,
>           delay_ms: delayBeforeAttempt,
>           outcome: retryable ? "retryable_error" : "non_retryable_error",
>           error: message,
>         });
>         if (!retryable || attempt === this.retryConfig.maxAttempts) {
>           return { final_status: "failed_after_retries", attempts };
>         }
>         delayBeforeAttempt = calculateRetryDelay(
>           attempt,
>           this.deps.random,
>           this.retryConfig,
>         );
>       }
>     }
>
>     // The loop returns from success or terminal failure; this guards future edits.
>     return { final_status: "failed_after_retries", attempts };

> ## Design decisions
>
> ### In-memory adapters behind interfaces
>
> The checkout handler depends on `IdempotencyStore`, `VehicleLock`, `ReservationRepository`, and `PaymentGateway` interfaces. The triage path accepts injected clock, sleeper, RNG, and alert sink. The supplied in-memory adapters make the assessment reproducible without infrastructure. Their atomic map operations are safe within one Node process; they do not coordinate multiple processes and their state does not survive restarts.
>
> ### Idempotency and lock ordering
>
> Checkout requires an idempotency key. The store claims it with one synchronous check-and-set operation; it never performs a separate read followed by a write. The request fingerprint binds the key to its booking, vehicle, customer, and amount. In-flight repeats return `409 REQUEST_IN_PROGRESS`, completed repeats replay the stored response, and a changed payload returns `422 IDEMPOTENCY_KEY_REUSED`.
>
> The checkout order is **idempotency key → vehicle lock/reservation → payment operations**. A token-owned vehicle lock uses a TTL and compare-token release; the repository also atomically reserves only an available vehicle. Payment capture happens only after the reservation is confirmed. A production implementation should use durable database transactions and an outbox for capture, as described in the RCA.
>
> ### Resilient dispatch
>
> Alerts are sorted by severity: critical, offline, then maintenance. The dispatcher retries timeout, network, and 5xx failures using full jitter over an exponential ceiling (200 ms base, 5,000 ms cap, five attempts). Non-retryable 4xx responses stop immediately. The alert ID is stable for a device, incident type, and run timestamp; the sink deduplicates by this ID so an accepted alert whose acknowledgment was lost is not accepted twice.
>
> ## Replacing the in-memory adapters
>
> - **PostgreSQL:** implement `IdempotencyStore` with a unique idempotency-key constraint and `INSERT ... ON CONFLICT DO NOTHING`; implement vehicle reservation with a conditional `UPDATE ... The exact schema and SQL flow are in [RCA.md](docs/RCA.md).
> - **Redis:** implement the vehicle lock with `SET lock:<vehicle_id> <owner-token> NX PX <ttl-ms>`. Release only with a Lua compare-and-delete script that checks the token. > - **Payment provider:** replace the mock with an adapter that uses a stable provider idempotency key for authorization and capture. Capture from a transactional outbox after the confirmed reservation commit, and reconcile uncertain outcomes.
> - **Alert webhook:** implement `AlertSink` with an HTTP client that sends `alert_id` as the receiver's idempotency key. Keep retry classification limited to timeouts, network failures, and server errors.
